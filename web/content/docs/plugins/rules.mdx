title: Rules
description: Instructions that arrive only where they apply
---

`AGENTS.md` reaches every agent whole, whatever it is touching. A rule
reaches it only when it matters: when the agent opens a file under
`src/ui/`, or when the task is a migration. Write each one once, in
`.agents/rules/`, and every agent reads it.

```markdown
---
trigger: glob
globs: "**/src/ui/**/*.rs"
---

Colours come from the theme: name a `Token`, never an RGB value.
```

## Where rules live

One Markdown file per rule, directly under `.agents/rules/` in your project,
committed with it. Each file's frontmatter says when it applies; the rest of
the file is the rule.

A subfolder is read only when `.agents/rules.json` registers it, which is how
Antigravity reads it, and so uze and the rules engine too:

```json
{"entries": [{"path": ".agents/rules/team"}]}
```

Each entry's `path` is relative to the root of the project, not to the
manifest. A folder entry reads the `*.md` files directly in it, and a file
entry reads that one file. `include_only` and `exclude` list paths relative to
the entry. A file registered twice is still one rule. A manifest that does not
parse registers nothing, and `uze status` says so. `inherits` is not followed:
uze reports it, because the rules it reaches arrive in Antigravity alone.

## When a rule arrives

| `trigger` | Arrives | Needs |
|---|---|---|
| `glob` | when the agent reads, edits or writes a file matching `globs` | `globs` |
| `model_decision` | as one line of an index; the agent reads the rule when the task calls for it | `description`, written as when to read it |
| `always_on` | at the start of every session | nothing more |
| `manual` | only when someone points the agent at it | nothing more |

Most rules are `glob`. Keep `always_on` rare: it costs every session, and text
that is always true usually belongs in `AGENTS.md`.

## Patterns

`globs` is one pattern, or several separated by commas. Quote it when it
starts with `*`. Each pattern is either:

- a file name, with no `/`, which matches at any depth: `*.sql`, `Makefile`
- a path that starts with `**/`: `**/src/ui/**`, `**/migrations/*.sql`

Inside a pattern, `**` matches any number of directories, `*` matches within
one name, `?` matches one character, and `[ab]` or `[0-9]` matches one
character of a set. Everything else, spaces included, is matched literally.

A directory pattern has to start with `**/` because Antigravity matches
against the file's full path: `src/ui/**` would never fire there, so uze
reports it rather than deliver it to some agents and not others. Braces
(`{a,b}`), negated sets (`[!a]`) and a leading `/`, `./` or `../` are
reported the same way. Write two patterns instead of braces.

## Write a rule as a convention

Say what the project does, not what the agent must answer: "Handlers return
`Result<_, ApiError>`", not "You MUST always reply with…". Keep one concern per
file and keep it short. The `uze:rules` skill guides an agent through writing
one:

```text
/uze:rules
```

## How each agent receives them

| Agent | Route |
|---|---|
| Antigravity | reads `.agents/rules/` and `.agents/rules.json` itself, with or without uze |
| Claude Code | through the rules engine `uze setup` installs |
| Codex | through the rules engine; a path named only inside a shell command is found on a best-effort basis |
| OpenCode | through the rules engine |

The engine reads your project's own `.agents/rules/` and `.agents/rules.json`
each time, so a branch or a checkout with different rules gets its own. The
engine copies nothing into your project, and nothing is compiled. On Windows the engine is not available yet,
and `uze status` says so.

## Share rules through a plugin

When the same conventions hold for every repository of a team, write them
once in a plugin instead of copying files between projects. A plugin ships
rules as Markdown files directly under its `rules/` directory, in the same
format. Scaffold one with:

```bash
uze agent plugin create acme-conventions --market acme --rules
```

`uze agent plugin check` validates the plugin's rules with the same checks as
`uze agent rules check`. Patterns are matched against paths relative to the
project that receives the rule.

### Declaring the plugin

In a project, `uze acme-conventions@acme` (or `uze install`, once the plugin
is in `agents.yaml`) copies each rule, byte for byte, into the project:

```text
.agents/rules/acme-conventions@acme/ui.md
.agents/rules/acme-conventions@acme/testing.md
```

and registers the folder in `.agents/rules.json`, creating it when there is
none:

```json
{
  "entries": [
    {
      "path": ".agents/rules/acme-conventions@acme"
    }
  ]
}
```

The folder names the plugin the files belong to. Every agent reads them
exactly as it reads your own rules, and a rule of yours with the same name is
left alone. uze adds and removes only its own entries in the manifest and
writes every other entry and key back unchanged. If the manifest does not
parse, uze leaves it as it is, copies nothing and says so. Rules are the one part of a plugin that never reaches an
agent machine-wide: `uze install -m` reports them as delivered per project,
and a project that does not declare the plugin never receives them.

An `always_on` rule is how a plugin says something to every agent of every
project that declares it.

### Commit the copies

The copies are ordinary project files. Commit them and `.agents/rules.json`
beside `agents.lock`: a clone, a worktree or CI then has the rules without
running uze, and Antigravity reads them there natively.

### Updates and drift

`uze update acme-conventions` moves the lock to the plugin's new revision
and rewrites its copies to match. Rules the new revision changed show up as
modified files in your pull request, and rules it dropped as deleted ones,
so a change to the conventions is reviewed like code. `uze remove
acme-conventions` deletes the plugin's copies, its folder and its entry, and
the manifest too once nothing else is left in it. Your own rules stay.

A copy is current when it matches the plugin's rule at the revision
`agents.lock` pins. `uze status` reports each plugin's rules as current, or
names every file that is drifted (edited), missing, or extra (in the plugin's
folder but not shipped by it). It can do that on a fresh clone too: when
this machine does not have the plugin, it reads the pinned revision without
installing anything, and without network it reports the copies as
unverified.

uze never overwrites or removes a copy someone edited. `uze install` and
`uze update` name it and leave it. To resolve it, either revert the file, or
take ownership of the change by moving it out of the plugin's folder into
`.agents/rules/`, which makes it one of your project's own rules. A missing copy is restored by
`uze install`.

## Check them

```bash
uze agent rules check
```

Validates every rule offline, the ones `.agents/rules.json` registers
included, and names each file that is not one and why, or the manifest when it
does not parse.
`uze status` reports the same: how many rules of each kind, any file that is
not a rule, each declared plugin's rules and whether their copies match the
lock, and how each installed agent receives them. It never prints a rule's
text.

In the workspace, the harness's details under **Manage** and the agent's
section of the space view show `.agents/rules` beside `AGENTS.md`: **Native**,
**Rules engine**, **Run uze setup** when the engine has not been installed for
that agent yet, or **Not supported**.
