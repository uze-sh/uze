---
title: Extensions
description: Add something to the workspace from a plugin, declared in KDL, scripted in Rhai, and allowed by whoever runs it
---

An extension is what a plugin adds to the [workspace](/docs/workspace#extensions):
a line in the bar under the agent area, a drawer beside the agent, a block of
the sidebar, a full-frame view. Harnesses never see it; only the workspace
does.

An extension never draws. It declares what it shows and where its data comes
from, and the workspace draws it, in the operator's theme and glyphs, with the
same keys and mouse as everything else there. Its logic runs in a bounded
script engine that reaches only what the operator allowed.

## Ask an agent

The `uze:author` skill writes extensions too:

```text
/uze:author add an extension to my plugin that lists the open items of TODO.md
```

The agent writes the files, checks them and installs the plugin. It cannot
allow the extension for you: it tells you what the extension asks for and
where to allow it.

Each extension is a directory under `extensions/`, named by its id, and a
plugin may carry several.

| File | What it holds |
| --- | --- |
| `extension.kdl` | The manifest, in [KDL](https://kdl.dev): the surfaces, where their data comes from, the actions, and the grants it asks for |
| `*.uze` | Components: a `<view>` block in KDL, built from the catalog's nodes, a `<script>` block in [Rhai](https://rhai.rs), or both |
| `fixtures/*.json` | A sample of what a source answers, for tests and for a view with no script |
| `tests/*.test.kdl` | Tests the check runs, and their snapshots |

To scaffold one into a plugin you are writing:

```bash
uze agent plugin create my-plugin --market my-market --extension todo
```

It writes a manifest with a full-frame view and a sidebar section, the
component they draw, a fixture, and tests that pass. The first time it writes
an extension into a marketplace, it also adds this line to the marketplace's
`.gitattributes`, creating the file if there is none, so forges highlight
components as KDL:

```text
*.uze linguist-language=KDL
```

## Where it shows

A surface names its slot:

| Slot | Where |
| --- | --- |
| `bar` | One line in the bar under the agent area, on the left or the right. A click opens the drawer or view it names |
| `drawer` | A panel on a side of the agent area, beside the pane or floating over it |
| `view` | The full frame, opened from its door in the bar |
| `section` | A block of the sidebar |
| `status` | One row of the sidebar's header |
| `band` | One to six rows along the top or bottom of each agent's pane |
| `overlay` | A card over the frame, opened by an action and closed by `Esc` |

A band's rows are taken before the agent's pane is sized, and a floating
drawer keeps the agent's terminal at its size, so neither makes the agent
rewrap what it printed.

## A worked example

This extension counts the open items of the checkout's `TODO.md` in the bar,
and lists them in a drawer a click on the count opens.

```kdl title="extensions/todo/extension.kdl"
protocol 1
id "todo"
name "Todo"
description "The open items of the checkout's TODO.md"

wants "read:checkout" "clipboard"

surface "count" slot="bar" view="count.uze" source="items" opens="list"
surface "list" slot="drawer" view="list.uze" source="items" title="Todo"

source "items" {
    script "items.uze"
    input file="TODO.md"
    applies-when "TODO.md"
    refresh-on "paths.changed" "TODO.md"
}

action "copy" label="Copy the item" on="list" key="ctrl-y" {
    clipboard "{text}"
}
```

The source runs the script in `items.uze` with its `input`, only in a
checkout that has a `TODO.md`, and again whenever that file changes. The
action copies the selected item. `wants` lists every grant the extension asks
for: the check refuses an action or a script that needs one it does not list.

Each view binds the source's data with `{field}`:

```kdl title="extensions/todo/count.uze"
<view>
Row gap=1 {
    Icon "check" role="info"
    Text "{count} open"
}
</view>
```

```kdl title="extensions/todo/list.uze"
<view>
Stack gap=1 {
    Text "{count} open in TODO.md" role="muted"
    List each="items" empty="Nothing open" {
        Text "{text}"
    }
}
</view>
```

A colour is always a role (`muted`, `info`, `warning`), never a value, and an
icon is named, never typed as a glyph: the theme and the glyph set the
operator chose decide how each one looks.

The script answers with an envelope whose `data` is what the views bind:

```rust title="extensions/todo/items.uze"
<script>
// Every line of the file that opens with `- [ ] `.
fn answer(input, context) {
    let open = [];
    for line in lines(read_checkout(input.file)) {
        if line.starts_with("- [ ] ") {
            open.push(#{ text: line.sub_string(6) });
        }
    }
    #{ data: #{ items: open, count: open.len() } }
}
</script>
```

`read_checkout` exists only because the manifest wants `read:checkout`. A
script has no `import` or `eval`, and is stopped past its bounds: a million
operations, 100 ms, 1 MiB strings.

A test opens a surface with a fixture in place of the script, and acts on it
as the operator would:

```json title="extensions/todo/fixtures/items.json"
{
  "count": 2,
  "items": [
    { "text": "Write the view" },
    { "text": "Check the plugin" }
  ]
}
```

```kdl title="extensions/todo/tests/todo.test.kdl"
test "the bar counts the open items" {
    surface "count"
    given "items" fixture="fixtures/items.json"
    expect-text "2 open"
}

test "the drawer lists them, and ctrl+y copies one" {
    surface "list"
    given "items" fixture="fixtures/items.json"
    expect-text "Check the plugin"
    press "ctrl+y"
    expect-action "copy"
    snapshot "list"
}
```

## Sources and actions

A source says where a surface's data comes from:

| Source | Answered by |
| --- | --- |
| `fixture` | A JSON file of the extension. Runs nothing, so it asks for no consent |
| `script` | The `answer` function of a component's `<script>` |
| `run` | A program, given as an argv and never through a shell: a file of the extension, or a program an `exec:` grant names |
| `agents` | The workspace: every agent of the open spaces and its state |
| `events` | The workspace: the last events the extension saw |
| `resident` | A script kept running while its surface is shown, with its own clock and keys, for a game or a live view |

A source asks again on a clock (`every "30s"`, while a surface showing it is
in view), when files beneath a path of the checkout change, when the
checkout's branch, head or working tree changes, or when an agent starts or
finishes a turn or a tool. An action is what a person can do on a surface: call a script
function, ask a source again, copy, open a file of the checkout, open another
surface, or type a prompt into an agent, which the workspace shows first and
sends only to an agent that is ready. Inputs (`Field`, `Select`, `Form`) and
preferences the operator sets on the Extensions screen feed both.

## Grants and consent

Installing a plugin is one question: may these files be stored and delivered
to your agents. An extension is code the workspace itself runs, so running it
is a second question, asked apart, about exactly what it may reach. Each
grant in `wants` is a line of that question:

| Grant | Lets the extension |
| --- | --- |
| `read:checkout` | Read files beneath the checkout's root |
| `clipboard`, `open-path` | Copy text, open a file of the checkout |
| `exec:<program>` | Run that program |
| `store`, `store:global` | Keep a small JSON record per project, or one for the machine |
| `notify` | Send a notification and a sound, rate-limited |
| `agent:observe` | See the workspace's agents and what they do |
| `agent:prompt` | Type a prompt into an agent, shown first |
| `net:<host>` | Fetch from that one host, over HTTPS |
| `mcp:<server>/<tool>` | Call one tool of an MCP server a plugin delivers |
| `resident` | Keep its script running while it is shown |

No grant writes the checkout. Ask for the fewest grants that do the job: each
one is what the operator is asked about.

- A view fed only by fixtures draws with no question asked. Anything that
  runs, a script, a program or an action calling one, waits until the
  operator allows its grants and enables it. Until then the surface says so
  where its data would be.
- Consent covers the exact files allowed. An update that wants the same
  grants or fewer is applied as it comes; one that wants a new grant is held
  until the operator allows it again.
- A program is pinned to the path found when it was allowed, never looked up
  on `PATH` again, and confined where the machine can: it reads the checkout
  and the system, writes only its own scratch folder and opens no socket.
  Where the machine cannot confine it, allowing it says it runs as you.
  `uze doctor` says which this machine is.
- Only the operator answers, on the workspace's Extensions screen or when
  `uze install` asks on a terminal. An agent cannot answer from its pane.

## Check, test and iterate

```bash
uze agent plugin check my-plugin                     # compile, bind and test every extension
uze agent plugin check my-plugin --update-snapshots  # write the snapshots a change you meant moved
uze agent plugin check my-plugin --run               # run the scripts against this checkout too
uze update my-plugin -m                              # deliver the change to the workspace
```

The check compiles every extension with the rules the workspace hosts it
with, refuses a script that calls a host function its grants do not give it,
binds each view to its fixture, and runs every `tests/*.test.kdl`. Each
finding names its file, line and column, and how to fix it.

A test runs nothing the plugin ships, so it passes the same on any machine.
It opens a surface, feeds it a fixture, then clicks, presses keys and expects
text or an action. `snapshot` keeps the cells it drew, as text and colour
roles rather than colours, so a theme change never breaks it. A snapshot
missing or changed fails the check until `--update-snapshots` writes it, and
the diff is yours to review.

## Editor support

`uze agent plugin lsp` is a language server for `extension.kdl`, components
and tests: completion and hover from the catalog, and the check's own
diagnostics as you type. Inside a `<script>` block it answers nothing yet.
Editors know no `.uze` language, so name one and point it at the server:

<Tabs items={["Helix", "Neovim", "VS Code"]}>
  <Tab value="Helix">

```toml title="languages.toml"
[language-server.uze]
command = "uze"
args = ["agent", "plugin", "lsp"]

[[language]]
name = "uze"
scope = "source.uze"
file-types = ["uze"]
language-servers = ["uze"]

[[language]]
name = "kdl"
language-servers = ["uze"]
```

  </Tab>
  <Tab value="Neovim">

```lua
vim.filetype.add({ extension = { uze = "uze" } })
vim.api.nvim_create_autocmd("FileType", {
  pattern = { "kdl", "uze" },
  callback = function()
    vim.lsp.start({
      name = "uze",
      cmd = { "uze", "agent", "plugin", "lsp" },
      root_dir = vim.fs.root(0, "extension.kdl"),
    })
  end,
})
```

  </Tab>
  <Tab value="VS Code">

Map `*.uze` to a language in your settings, then point any generic LSP client
extension at `uze agent plugin lsp` for the `kdl` and `uze` languages:

```json title="settings.json"
{ "files.associations": { "*.uze": "uze" } }
```

  </Tab>
</Tabs>

The `uze:author` skill's
[extension guide](https://github.com/uze-sh/uze/blob/main/plugins/uze/skills/author/references/extension.md)

holds the official extensions, with their tests, to read as examples.
